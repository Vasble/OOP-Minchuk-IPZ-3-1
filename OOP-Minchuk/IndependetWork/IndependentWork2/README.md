# IndependentWork2 — Процедурний і об'єктний підходи: порівняння

Консольний проєкт (.NET 8), що реалізує обчислення кошика інтернет-магазину
двома способами: процедурно (`ProceduralDemo.cs`) і об'єктно
(`ObjectOrientedDemo.cs`). Обидві версії викликаються по черзі з `Main`
(`Program.cs`) на одному і тому самому наборі тестових товарів, тому
підсумкові суми збігаються.

## Запуск

```
dotnet run
```

## Тестові товари (однакові для обох версій)

| Товар      | Ціна, грн | Кількість |
|------------|-----------|-----------|
| Ноутбук    | 25000     | 1         |
| Мишка      | 350       | 2         |
| Клавіатура | 800       | 1         |
| Навушники  | 600       | 1         |
| Флешка     | 250       | 3         |

Підсумок обох версій: **25210.00 грн**.

## Проблеми процедурної версії

1. Дані про один товар розкидані по трьох паралельних масивах
   (`names`, `prices`, `quantities`) — немає єдиної сутності "товар",
   тому доступ до всіх даних про товар вимагає ручної синхронізації
   індексів у трьох масивах одразу.
2. Немає жодної гарантії, що всі три масиви мають однакову довжину.
   Якщо додати елемент лише в один з них, помилка (або тихе зміщення
   даних) виявиться лише під час виконання, а не на етапі компіляції.
3. Логіку знижки (`ApplyDiscount`) неможливо перевикористати в іншому
   сценарії (наприклад, для оптового прайсу чи іншого кошика) без
   копіювання коду — вона жорстко прив'язана саме до цих масивів.
4. Додавання нового товару вимагає синхронної зміни одразу трьох
   масивів у правильному порядку — легко помилитись.
5. Немає інкапсуляції: будь-яка частина програми може змінити масив
   цін окремо від масиву назв, і ніщо не захищає узгодженість даних.

## Порівняння підходів

| Критерій | Процедурна версія | Об'єктна версія |
|---|---|---|
| Структура даних | Три паралельні масиви (`string[]`, `double[]`, `int[]`), пов'язані лише спільним індексом | Клас `Product` (назва, ціна) + клас `CartItem` (товар + кількість), об'єднані у `List<CartItem>` всередині `Cart` |
| Цілісність даних | Нічим не гарантована — індекси можна розсинхронізувати | Гарантована — кожен `CartItem` завжди містить пов'язані назву, ціну й кількість разом |
| Логіка знижки | Окрема функція `ApplyDiscount`, що працює напряму з масивами | Властивість `DiscountedLineTotal` — частина `CartItem`, обчислюється поруч із даними товару |
| Додати нову операцію (напр., видалення товару) | Потрібно писати функцію, що видаляє елемент одразу з трьох масивів синхронно, ризикуючи розсинхронізувати їх | Достатньо додати метод `RemoveItem` у `Cart`, що видаляє один `CartItem` зі списку — дані лишаються цілісними автоматично |
| Повторне використання в іншому місці програми | Складно: треба тягнути за собою всі три масиви й усі функції, що з ними працюють | Просто: достатньо створити ще один об'єкт `Cart` і викликати `AddItem`/`GetTotal` — вся логіка інкапсульована всередині класу |

**Висновок:** об'єктна версія не змінює саму бізнес-логіку (сума, знижка,
підсумок ідентичні — 25210.00 грн в обох випадках), але об'єднує дані й
поведінку в одну сутність. Це усуває ризик розсинхронізації паралельних
масивів і робить код легшим для розширення та повторного використання.
