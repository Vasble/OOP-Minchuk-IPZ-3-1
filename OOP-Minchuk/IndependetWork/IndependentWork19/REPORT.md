# Звіт до самостійної роботи №19

**Тема:** Дизайн винятків і політики retry: теорія та кейси Polly
**Проєкт:** `IndependentWork19` (.NET 10, Polly.Core 8)

Предметна область — **інтернет-магазин**:
- склад, де резервуються товари (власний виняток);
- три зовнішні залежності, які можуть тимчасово збоїти (сценарії Polly).

## 1. Власний тип винятку `InsufficientStockException`

```csharp
public class InsufficientStockException : Exception
{
    public string ProductSku { get; } = string.Empty;
    public int RequestedQuantity { get; }
    public int AvailableQuantity { get; }
    public int Shortage => Math.Max(0, RequestedQuantity - AvailableQuantity);

    public InsufficientStockException() : base("Недостатньо товару на складі.") { }
    public InsufficientStockException(string message) : base(message) { }
    public InsufficientStockException(string message, Exception innerException) : base(message, innerException) { }

    public InsufficientStockException(string productSku, int requestedQuantity, int availableQuantity)
        : base($"Недостатньо товару '{productSku}': запитано {requestedQuantity} шт., доступно {availableQuantity} шт.")
    { ... }
}
```

- Назва закінчується на `Exception`, клас успадковує `System.Exception`.
- Реалізовано **три стандартні конструктори** (без параметрів, з `message`, з `message` + `innerException`) і один доменний.
- Додаткові властивості `ProductSku`, `RequestedQuantity`, `AvailableQuantity` і обчислювана `Shortage` дають обробнику помилки контекст. Наприклад, можна запропонувати клієнту замовити 2 шт. замість 5, і для цього не треба розбирати текст повідомлення.

**Демонстрація в `Main`** (`Warehouse.Reserve`):
- блоки `catch` йдуть **від специфічного до загального**: `InsufficientStockException` → `KeyNotFoundException` → `ArgumentException`;
- `finally` виконується завжди, і після успіху, і після помилки;
- конструктор з `innerException` загортає низькорівневу `IOException` («сервер постачальника розірвав з'єднання») у доменний виняток, зберігаючи першопричину.

```
✘ InsufficientStockException: Недостатньо товару 'LAPTOP-15': запитано 5 шт., доступно 2 шт.
    Sku=LAPTOP-15, Requested=5, Available=2, Shortage=3
    finally: запит (LAPTOP-15, 5) оброблено, з'єднання зі складом закрито.
✘ Не вдалося оновити залишки товару 'LAPTOP-15' у постачальника.
    InnerException: IOException — Сервер постачальника розірвав з'єднання.
```

## 2. Сценарій 1 — Retry з експоненційною затримкою та jitter (курс валют з API НБУ)

**Проблема.** Магазин показує ціни в гривнях і бере курс USD/EUR із зовнішнього API. Таке API час від часу повертає `503 Service Unavailable` або не відповідає вчасно (перевантаження, перезапуск сервера). Збої **короткочасні**: через пів секунди той самий запит зазвичай проходить.

**Чому Retry.**
- Помилка тимчасова, а операція (отримати курс) **ідемпотентна**: повторний `GET` нічого не змінює і нічого не дублює. Тож повторювати безпечно.
- **Експоненційна** затримка (200 → 400 → 800 → 1600 мс) дає сервісу час відновитися і не засипає його запитами.
- **Jitter** робить затримку випадковою, тож сотні клієнтів не повторюють запити синхронно.
- `ShouldHandle` обмежує повтори **лише тимчасовими** помилками (`HttpRequestException`, `TimeoutException`). Помилка в даних (`ArgumentException`) не виправиться від повтору.

```csharp
new ResiliencePipelineBuilder()
    .AddRetry(new RetryStrategyOptions
    {
        ShouldHandle = new PredicateBuilder().Handle<HttpRequestException>().Handle<TimeoutException>(),
        MaxRetryAttempts = 4,
        Delay = TimeSpan.FromMilliseconds(200),
        BackoffType = DelayBackoffType.Exponential,
        UseJitter = true,
        OnRetry = args => { Log.Polly($"Retry #{args.AttemptNumber + 1}: ... Чекаємо {args.RetryDelay.TotalMilliseconds:F0} мс..."); return default; }
    })
    .Build();
```

**Вивід і пояснення:**

```
--- 1a. API тричі збоїть, потім відповідає ---
POLLY Retry #1: HttpRequestException — 503 Service Unavailable ... Чекаємо 133 мс...
POLLY Retry #2: TimeoutException — API НБУ не відповів вчасно. Чекаємо 192 мс...
POLLY Retry #3: HttpRequestException — 503 Service Unavailable ... Чекаємо 537 мс...
OK    Курс USD = 41.85 грн. Викликів API: 4
--- 1b. Помилка у вхідних даних — повторювати немає сенсу ---
ERROR Не повторюємо (ArgumentException не входить до ShouldHandle): Некоректний код валюти 'US'. Викликів API: 1
--- 1c. API лежить довго — спроби вичерпано ---
POLLY Retry #1 ... #4 ... Чекаємо 176 / 186 / 265 / 1177 мс...
ERROR Остаточна невдача після 5 спроб: HttpRequestException — 503 ... Показуємо останній збережений курс.
```

- **1a:** три збої поспіль користувач не помічає, бо четверта спроба повертає курс.
- **1b:** некоректний код валюти дає лише 1 виклик, без марних повторів.
- **1c:** після `MaxRetryAttempts = 4` (усього 5 викликів) Polly прокидає останній виняток, і код обробляє його у `catch`.

Затримки ростуть приблизно вдвічі (база 200, 400, 800, 1600 мс), але не точно. Це наслідок jitter: Polly використовує алгоритм «decorrelated jitter», тому значення випадкові навколо експоненційної кривої.

## 3. Сценарій 2 — Circuit Breaker (платіжний шлюз)

**Проблема.** Під час оформлення замовлення магазин викликає платіжний шлюз. Якщо шлюз «ліг» на кілька хвилин, кожен запит чекає відповіді й повертає `502 Bad Gateway`. Це створює дві проблеми:
- користувачі довго чекають помилки;
- потоки сервера зайняті марними запитами, а сам шлюз, який намагається піднятися, отримує ще більше навантаження.

**Чому Circuit Breaker, а не Retry.** Довга серія помилок означає, що сервіс недоступний **тривалий час**. Retry лише помножив би кількість марних запитів.

Circuit Breaker поводиться інакше:
- рахує частку помилок;
- після порогу **розмикає ланцюг** (Open) і миттєво відхиляє наступні запити, взагалі не викликаючи шлюз;
- через `BreakDuration` пропускає один пробний запит (Half-Open);
- якщо пробний запит успішний, знову замикає ланцюг (Closed).

Відхилені замовлення не втрачаються: їх ставлять у чергу на повторну оплату.

Платіж — **неідемпотентна** операція: повтор може списати гроші двічі. Тому сліпий Retry для неї небезпечний.

```csharp
new ResiliencePipelineBuilder()
    .AddCircuitBreaker(new CircuitBreakerStrategyOptions
    {
        ShouldHandle = new PredicateBuilder().Handle<PaymentGatewayException>(),
        FailureRatio = 0.5,
        MinimumThroughput = 4,
        SamplingDuration = TimeSpan.FromSeconds(10),
        BreakDuration = TimeSpan.FromSeconds(1.5),
        StateProvider = stateProvider,
        OnOpened = args => { ... }, OnHalfOpened = _ => { ... }, OnClosed = _ => { ... }
    })
    .Build();
```

**Вивід і пояснення:**

```
--- 2a. Шлюз працює ---
OK    Замовлення #1: оплачено 625 грн, TX-0001-625 [Closed, 46 мс]
OK    Замовлення #2: оплачено 750 грн, TX-0002-750 [Closed, 30 мс]
--- 2b. Шлюз впав ---
ERROR Замовлення #3: 502 Bad Gateway — платіжний шлюз не відповідає. [Closed, 32 мс]
POLLY Circuit OPEN: забагато помилок (502 Bad Gateway ...). Запити блокуються на 1.5 с.
ERROR Замовлення #4: 502 Bad Gateway — платіжний шлюз не відповідає. [Open, 33 мс]
WARN  Замовлення #5: відхилено миттєво — BrokenCircuitException, шлюз не викликався. ... [Open, 0 мс]
...   (замовлення #6–#9 так само, 0 мс)
INFO  Спроб оплати: 9, реальних звернень до шлюзу: 4.
--- 2c. Шлюз відновився, чекаємо завершення BreakDuration ---
POLLY Circuit HALF-OPEN: пропускаємо пробний запит, щоб перевірити, чи шлюз відновився.
POLLY Circuit CLOSED: шлюз відновився, запити знову проходять.
OK    Замовлення #10..#12: оплачено ... [Closed]
INFO  Разом спроб оплати: 12, реальних звернень до шлюзу: 7.
```

- Після 4 викликів (2 успішні + 2 помилки, частка помилок 0.5 ≥ `FailureRatio`) ланцюг розімкнувся.
- Замовлення #5–#9 відхилено **за 0 мс замість ~30 мс**, і шлюз їх узагалі не отримав. Тобто 5 марних звернень до шлюзу було зекономлено.
- Після паузи пробний запит пройшов успішно, і ланцюг автоматично замкнувся. Програма повернулася до нормальної роботи без ручного втручання.

## 4. Сценарій 3 — Timeout + Retry + Fallback (рекомендації на сторінці товару)

**Проблема.** На сторінці товару показано блок «Вам також може сподобатися», який заповнює окремий сервіс рекомендацій. Під навантаженням цей сервіс інколи **зависає** на секунди. Сторінка не повинна чекати, бо рекомендації — другорядний блок. Краще показати щось просте, ніж змусити клієнта дивитися на завантаження.

**Чому така комбінація.** Стратегії додаються в конвеєр ззовні всередину:

1. **Timeout (300 мс)**, внутрішня стратегія. Обмежує кожну спробу. Якщо сервіс не відповів, Polly скасовує операцію через `CancellationToken` і кидає `TimeoutRejectedException`. Без тайм-ауту Retry і Fallback не допомогли б, бо зависла спроба ніколи б не завершилася помилкою.
2. **Retry (2 повтори, 100 мс)**, середня стратегія. Зависання часто разове, тож ще одна спроба має шанс вкластися в час. Запит рекомендацій ідемпотентний.
3. **Fallback**, зовнішня стратегія. Якщо всі спроби невдалі, повертає кешований список хітів продажів. Сторінка завжди отримує результат, а користувач не бачить помилки.

Загальний час у найгіршому випадку обмежений: 3 × 300 мс + 2 × 100 мс ≈ 1.1 с.

```csharp
new ResiliencePipelineBuilder<List<string>>()
    .AddFallback(new FallbackStrategyOptions<List<string>>
    {
        ShouldHandle = new PredicateBuilder<List<string>>().Handle<TimeoutRejectedException>().Handle<HttpRequestException>(),
        FallbackAction = _ => Outcome.FromResultAsValueTask(CachedBestSellers),
        OnFallback = args => { ... }
    })
    .AddRetry(new RetryStrategyOptions<List<string>>
    {
        ShouldHandle = new PredicateBuilder<List<string>>().Handle<TimeoutRejectedException>(),
        MaxRetryAttempts = 2,
        Delay = TimeSpan.FromMilliseconds(100),
        BackoffType = DelayBackoffType.Constant,
        OnRetry = args => { ... }
    })
    .AddTimeout(new TimeoutStrategyOptions { Timeout = TimeSpan.FromMilliseconds(300), OnTimeout = args => { ... } })
    .Build();
```

**Вивід і пояснення:**

```
--- 3a. Сервіс відповідає швидко ---
OK    Клієнт 101: Бездротові навушники; ... [викликів сервісу: 1, загальний час: 131 мс]
--- 3b. Перша спроба зависла, друга вклалася в час ---
POLLY Timeout: сервіс не відповів за 300 мс, спробу скасовано.
POLLY Retry #1 після тайм-ауту, чекаємо 100 мс.
OK    Клієнт 102: Бездротові навушники; ... [викликів сервісу: 2, загальний час: 573 мс]
--- 3c. Сервіс перевантажений: усі спроби завислі ---
POLLY Timeout ... → Retry #1 → Timeout ... → Retry #2 → Timeout ...
POLLY Fallback: сервіс недоступний (TimeoutRejectedException), повертаємо кешовані хіти продажів.
OK    Клієнт 103: Павербанк 20000 mAh (хіт продажів); ... [викликів сервісу: 3, загальний час: 1108 мс]
```

- **3a:** конвеєр не заважає, коли все добре: 1 виклик, жодних накладних витрат.
- **3b:** сервіс «завис» би на 2 секунди, але тайм-аут обірвав спробу через 300 мс, а повтор отримав відповідь. Разом 573 мс замість 2000+.
- **3c:** навіть коли сервіс зовсім не відповідає, сторінка отримує кешовані рекомендації за ~1.1 с, і винятків у коді, що викликає конвеєр, немає.

## 5. Коли кидати виняток, а коли повертати `Result<T>`

У проєкті є обидва підходи для однієї операції резервування:
- `Warehouse.Reserve` кидає `InsufficientStockException`;
- `Warehouse.TryReserve` повертає `Result<Reservation>`.

**Виняток** доречний, коли метод **не може виконати свій контракт** через ситуацію, яка не є нормальною частиною сценарію. Наприклад:
- зник зв'язок із базою;
- пошкоджено файл конфігурації;
- код викликали з некоректними аргументами (помилка програміста).

Переваги: виняток неможливо випадково проігнорувати, він несе стек викликів, і його можна обробити на тому рівні, де це має сенс.

**`Result<T>`** (або `bool TryXxx(out ...)`) підходить для **очікуваних** неуспіхів, які є частиною бізнес-логіки:
- товару не вистачає;
- користувач ввів неправильний пароль;
- запис не знайдено;
- форма не пройшла валідацію.

Такі ситуації трапляються постійно, тож їх не варто «вибухати» винятками: це повільніше (розкрутка стека) і заважає читати потік коду. Сигнатура `Result<T>` прямо каже викликачу, що треба обробити обидва варіанти.

**Правило:** якщо неуспіх — нормальна частина роботи методу, повертайте `Result`. Якщо це справді виняткова ситуація, кидайте виняток. У веб-магазині брак товару — звичайна подія, тому для сторінки кошика краще `TryReserve`. А `Reserve` з винятком доречний там, де резерв **мав би** гарантовано пройти, наприклад після попередньої перевірки.

## 6. Загальні висновки щодо Polly

**Переваги:**
- Стратегії відмовостійкості описуються **декларативно** і **відокремлено від бізнес-логіки**. Код `GetRateAsync` нічого не знає про повтори.
- Стратегії легко **комбінувати** (Fallback → Retry → Timeout) і змінювати параметри без переписування коду.
- Готові та перевірені реалізації складних речей: експоненційна затримка з decorrelated jitter, Circuit Breaker зі станами й вибіркою за часом, кооперативний тайм-аут через `CancellationToken`.
- Колбеки (`OnRetry`, `OnOpened`, `OnTimeout`, `OnFallback`) дають готові точки для логування й метрик.
- Конвеєр (`ResiliencePipeline`) потокобезпечний, його створюють один раз і використовують повторно. Також є інтеграція з DI та `HttpClient` (`Microsoft.Extensions.Http.Resilience`).

**Обмеження:**
- Polly **не робить операцію безпечною для повтору**. Retry для неідемпотентних операцій (платежі, відправлення листів) може дублювати дії. Потрібні ключі ідемпотентності або інший патерн, як Circuit Breaker у сценарії 2.
- Тайм-аут **кооперативний**: він працює, лише якщо операція поважає `CancellationToken`. Синхронний код, який не перевіряє токен, Polly не зупинить.
- Неправильні параметри шкодять. Забагато повторів або короткий `BreakDuration` посилюють навантаження на сервіс, що й так погано працює, а занадто великий тайм-аут нічого не захищає.
- Polly додає залежність і складність. Для простих випадків вистачить кількох рядків `try/catch`, а для складних треба розуміти порядок стратегій у конвеєрі.
- Polly лише **маскує** проблеми інфраструктури. Помилки все одно треба логувати й моніторити, інакше система буде «тихо» працювати на запасних даних.

## 7. Відповіді на контрольні запитання

**1. Різниця між «кидати виняток» і «повертати Result». Приклади.**
Виняток перериває нормальний потік і передає керування найближчому підходящому `catch` вище в стеку. Він для ситуацій, коли метод не може виконати контракт.
*Приклад:* `File.ReadAllText("config.json")` кидає `FileNotFoundException`, бо без конфігурації програма працювати не може.

`Result` — це звичайне значення, яке явно повідомляє про успіх чи неуспіх. Він для очікуваних неуспіхів.
*Приклад:* `int.TryParse(input, out int value)` повертає `false` для некоректного вводу користувача. Це нормальна ситуація, і обробляти її треба одразу, без `try/catch`.
У проєкті: `Reserve` кидає `InsufficientStockException`, а `TryReserve` повертає `Result<Reservation>`.

**2. Які три стандартні конструктори рекомендується реалізовувати?**
- `MyException()` — без параметрів;
- `MyException(string message)` — з повідомленням;
- `MyException(string message, Exception innerException)` — з повідомленням і першопричиною, щоб загорнути низькорівневий виняток, не втративши його.

Додатково можна мати доменні конструктори з власними властивостями.

**3. Чим Circuit Breaker відрізняється від Retry? Коли який доцільніший?**
Retry **повторює** невдалу операцію, сподіваючись, що наступна спроба буде успішною. Він підходить для короткочасних, поодиноких збоїв (мережевий «блім», перевантаження на долю секунди) та ідемпотентних операцій.

Circuit Breaker **припиняє** звернення до сервісу після серії помилок і на якийсь час відхиляє запити одразу. Він підходить, коли сервіс недоступний довго: щоб не марнувати ресурси, не чекати тайм-аутів і дати сервісу відновитися.

Їх часто поєднують: Retry для поодиноких збоїв, а Circuit Breaker зупиняє повтори, коли збоїв забагато.

**4. Для чого потрібен Bulkhead і яку проблему він розв'язує?**
Bulkhead («перегородка») обмежує кількість одночасних операцій до певного ресурсу. Наприклад, не більше 10 паралельних запитів до API рекомендацій і черга на 20.

Він розв'язує проблему **каскадного збою**. Без обмеження повільний сервіс займе всі потоки і з'єднання застосунку, і тоді «ляже» навіть та частина, що з ним не пов'язана (оплата, кошик).
Bulkhead ізолює проблему в одному «відсіку».

У Polly v8 він реалізується через `AddConcurrencyLimiter` з пакета `Polly.RateLimiting`.

**5. Чому важливий Jitter при експоненційній затримці?**
Якщо сервіс упав, усі клієнти отримали помилку майже одночасно. З чистою експоненційною затримкою вони всі повторять запит **одночасно** (через 1 с, потім 2 с, 4 с...), створюючи хвилі навантаження («thundering herd»), що можуть знову покласти сервіс, який щойно піднявся.

Jitter додає кожному клієнту випадкову складову затримки. Повтори розподіляються в часі рівномірно, і навантаження стає плавним. У виводі сценарію 1 видно, що затримки не 200/400/800/1600 мс, а випадкові навколо цієї кривої.

**6. Які ризики виникають при Retry неідемпотентної операції?**
Неідемпотентна операція при повторі **змінює стан ще раз**: повторний платіж, другий лист клієнту, дубль замовлення.

Найнебезпечніший випадок — тайм-аут. Клієнт не дочекався відповіді, але сервер **встиг** виконати операцію. Повтор виконає її вдруге, і гроші спишуться двічі.

Щоб цього уникнути:
- використовують ключ ідемпотентності (унікальний Id запиту, за яким сервер розпізнає дубль);
- перед повтором перевіряють статус операції;
- для таких операцій не використовують автоматичний Retry, а обирають Circuit Breaker і чергу відкладеної обробки (як у сценарії 2).
