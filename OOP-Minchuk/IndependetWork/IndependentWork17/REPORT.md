# Звіт до самостійної роботи №17

**Тема:** LINQ pipelines: ETL та аналітика
**Проєкт:** `IndependentWork11` (.NET 10)

## 1. Модель даних і тестові дані

| Сутність | Поля | Кількість |
|----------|------|-----------|
| `Product` | `Id`, `Name`, `Category`, `UnitPrice` | 60 (6 категорій × 10 товарів) |
| `Customer` | `Id`, `Name`, `City` | 80 (10 міст України) |
| `Sale` | `Id`, `ProductId`, `Quantity`, `SaleDate`, `CustomerId` | 1000 (01.2025 – 10.2026) |

## 2. Опис пайплайнів

Кожен пайплайн — окремий метод класу `SalesAnalytics` з назвою, яка пояснює, що він рахує. Тому `Main` лише викликає методи й виводить результати.

### Пайплайн 1 — `TopProductsByCategory()`: найпопулярніші продукти за категоріями

```csharp
_data.Sales
    .GroupBy(sale => sale.ProductId)
    .Select(group => new { ProductId = group.Key, TotalQuantity = group.Sum(sale => sale.Quantity) })
    .Join(_data.Products, totals => totals.ProductId, product => product.Id,
          (totals, product) => new { product.Name, product.Category, totals.TotalQuantity })
    .GroupBy(item => item.Category)
    .Select(categoryGroup => new CategoryTopProducts(categoryGroup.Key,
        categoryGroup.OrderByDescending(item => item.TotalQuantity).ThenBy(item => item.Name)
                     .Take(3).Select(item => new ProductSales(item.Name, item.TotalQuantity)).ToList()))
    .OrderBy(result => result.Category)
    .ToList();
```

**Мета:** для кожної категорії знайти 3 товари, яких продано найбільше штук.

| Оператор | Навіщо |
|----------|--------|
| `GroupBy(ProductId)` + `Sum` | Зводить 1000 продажів до ~60 рядків «товар → загальна кількість». Агрегація йде **до** `Join`, тож з'єднувати доводиться 60 рядків, а не 1000 |
| `Join` з `Products` | Додає назву й категорію товару |
| `GroupBy(Category)` | Розбиває товари на категорії |
| `OrderByDescending` + `ThenBy` + `Take(3)` | Сортує всередині кожної категорії й бере топ-3. `ThenBy(Name)` робить порядок стабільним, якщо кількості однакові |
| `OrderBy(Category)` | Виводить категорії за алфавітом |

**Результат:** найпопулярніші товари — «Кобзар» (218 шт.) у книгах і «Смартфон» (167 шт.) в електроніці.

### Пайплайн 2 — `RevenueByCity()`: загальний дохід за містами клієнтів

```csharp
_data.Sales
    .Join(_data.Products, sale => sale.ProductId, product => product.Id,
          (sale, product) => new { sale.CustomerId, Revenue = sale.Quantity * product.UnitPrice })
    .Join(_data.Customers, item => item.CustomerId, customer => customer.Id,
          (item, customer) => new { customer.City, item.CustomerId, item.Revenue })
    .GroupBy(item => item.City)
    .Select(cityGroup => new CityRevenue(cityGroup.Key, cityGroup.Sum(item => item.Revenue),
        cityGroup.Count(), cityGroup.Select(item => item.CustomerId).Distinct().Count()))
    .OrderByDescending(result => result.Revenue)
    .ToList();
```

**Мета:** дізнатися, з яких міст надходить найбільше доходу.

| Оператор | Навіщо |
|----------|--------|
| `Join` з `Products` | Дає `UnitPrice`. Дохід обчислюється одразу в проєкції (`Quantity * UnitPrice`) |
| `Join` з `Customers` | Дає місто клієнта |
| `GroupBy(City)` | Групує продажі за містом |
| `Sum`, `Count`, `Distinct().Count()` | Загальний дохід, кількість продажів і кількість різних клієнтів у місті |
| `OrderByDescending(Revenue)` | Сортує за доходом, від більшого до меншого |

Для `Revenue` використано `decimal`, а не `double`, щоб не накопичувалися похибки округлення в грошових сумах.

**Перевірка коректності:** той самий звіт реалізовано вручну на циклах і словниках (`RevenueByCityManual`). Програма порівнює результати через `SequenceEqual`, і вони збігаються.

**Результат:** Київ дає 24,1% доходу, далі Харків (15,2%) і Рівне (11,2%).

### Пайплайн 3 — `SalesByMonth()`: продажі за місяцями та роками

```csharp
_data.Sales
    .Join(_data.Products, sale => sale.ProductId, product => product.Id,
          (sale, product) => new { sale.SaleDate.Year, sale.SaleDate.Month, sale.Quantity,
                                   Revenue = sale.Quantity * product.UnitPrice })
    .GroupBy(item => new { item.Year, item.Month })
    .Select(group => new MonthlySales(group.Key.Year, group.Key.Month,
        group.Sum(item => item.Quantity), group.Sum(item => item.Revenue), group.Count()))
    .OrderBy(result => result.Year)
    .ThenBy(result => result.Month)
    .ToList();
```

**Мета:** побачити динаміку продажів у часі.

| Оператор | Навіщо |
|----------|--------|
| `Join` з `Products` | Дохід вимагає ціни |
| `GroupBy(new { Year, Month })` | Складений ключ з анонімного типу. Анонімні типи порівнюються за значеннями всіх полів, тож січень 2025 і січень 2026 — різні групи |
| `Sum` × 2, `Count` | Одиниці, дохід, кількість продажів |
| `OrderBy(Year).ThenBy(Month)` | Хронологічний порядок. `ThenBy` уточнює сортування, а не скасовує попереднє |

**Результат:** 22 місяці. За 2025 рік — 1645 одиниць на 4,45 млн грн. Найприбутковіший місяць — січень 2026 (542 766 грн).

### Пайплайн 4 (додатковий) — `TopCustomersWithFavoriteCategory()`: найцінніші клієнти

**Мета:** знайти найбільш цінних клієнтів (витрати вище середнього і щонайменше 5 замовлень) і категорію, на яку кожен з них витрачає найбільше. Це корисно, наприклад, для персональних пропозицій.

Оператори: `Join`, `GroupBy` (двічі, вкладено), `Select`, `Sum`, `Count`, **`Aggregate`**, `Average`, `Where`, `OrderByDescending`, `Take`.
- Вкладений `GroupBy(Category)` всередині групи клієнта рахує витрати за кожною категорією.
- `Aggregate((best, next) => next.Spent > best.Spent ? next : best)` знаходить категорію з максимальними витратами за один прохід, без сортування.
- `Average` один раз обчислює середні витрати, а `Where` за цим порогом відбирає клієнтів. Проміжний результат матеріалізовано в `ToList()`, щоб не обчислювати все двічі (для `Average` і для `Where`).

**Результат:** у топ-10 клієнтів лише дві улюблені категорії: «Електроніка» і «Спорт». Найдорожчі покупки належать саме до них.

## 3. Вимірювання продуктивності

Для кожного пайплайну створюється **новий** `Stopwatch` (метод `Measure.Run`). Вимірюються:
- **перший запуск** — разом із JIT-компіляцією;
- **середнє з 50 повторних запусків** — «прогрітий» код.

Режим `Release`, .NET 10. Кожен пайплайн закінчується `ToList()`, тому час включає повне виконання запиту, а не лише його побудову.

## 4. Аналіз результатів

1. **Перший запуск у 10–40 разів повільніший за наступні.** Під час першого виклику JIT компілює в машинний код методи LINQ для кожної комбінації узагальнених типів (анонімні типи, `record`), а ще ініціалізуються внутрішні структури. Тому для оцінки швидкості важливий прогрітий час, а перший запуск треба вимірювати окремо.
2. **Усі пайплайни працюють за лінійний час, O(n).** Кожен оператор (`GroupBy`, `Join`, `Sum`) проходить дані один раз, тож у 100 разів більше продажів дають приблизно в 20–60 разів більший час. `Join` у LINQ to Objects внутрішньо будує хеш-таблицю (`Lookup`) для внутрішньої колекції. Тому це не вкладений цикл O(n·m), а O(n + m).
3. **Пайплайн 1 найшвидший і масштабується найкраще.** Він агрегує (`GroupBy(ProductId)`) **до** `Join`, тож далі обробляється лише 60 рядків замість 100 000. Порядок операторів має велике значення: фільтруйте й агрегуйте якомога раніше.
4. **Пайплайни 2 і 3 найдорожчі.** Вони спершу з'єднують **кожен** продаж з довідниками (у пайплайні 2 двічі) і створюють проміжний анонімний об'єкт на кожен рядок. Це багато виділень пам'яті й роботи для збирача сміття (GC). `GroupBy` за рядком (`City`) або анонімним ключем (`Year, Month`) теж дорожчий, ніж за `int`.
5. **LINQ проти ручних циклів.** На 1000 рядках різниця в межах шуму (менше 1 мс). На 100 000 рядках ручна версія пайплайну 2 приблизно в 2,5 раза швидша (11 мс проти 28 мс), бо:
   - словники цін і міст будуються один раз;
   - немає проміжних анонімних об'єктів;
   - немає ітераторів і викликів делегатів на кожен елемент.

   Але ручна версія займає 40 рядків коду проти 15 і її важче читати та змінювати.
6. **Інші фактори, що впливають на час:**
   - збирач сміття (GC);
   - розмір ключа групування (`int` хешується швидше, ніж `string`);
   - кількість груп;
   - тип `decimal` (арифметика `decimal` повільніша, ніж `double`, але точна для грошей);
   - кеш процесора;
   - фонові процеси на комп'ютері (тому береться середнє з багатьох запусків).

## 5. Висновки щодо ефективності LINQ для ETL та аналітики

- LINQ дуже добре підходить для **аналітичних і ETL-завдань у пам'яті**. Пайплайн читається як опис задачі: «з'єднати → згрупувати → порахувати → відсортувати». Його легко змінювати й перевіряти.
- На типових обсягах (тисячі – десятки тисяч записів) пайплайни виконуються за кілька мілісекунд. Різниця з ручними циклами для користувача непомітна.
- На великих обсягах LINQ має накладні витрати: делегати, ітератори, проміжні об'єкти. Якщо пайплайн стає вузьким місцем, його оптимізують:
  - агрегують і фільтрують раніше;
  - зменшують кількість `Join`;
  - матеріалізують повторно використовувані результати (`ToList`, `ToDictionary`);
  - лише в крайньому разі переписують гарячу ділянку на цикли.
- Для справжніх ETL-обсягів (мільйони рядків у базі даних) обчислення краще переносити в СУБД (EF Core перетворює LINQ на SQL), а в пам'яті — розглянути PLINQ.

## 6. Відповіді на контрольні запитання

**1. Які переваги дає LINQ для ETL-пайплайнів порівняно з ручними циклами?**
- Декларативність: код описує, *що* треба отримати, а не *як* обходити дані.
- Менше коду (15 рядків замість 40 у пайплайні 2) і менше місць для помилок: не треба вручну створювати словники, лічильники й перевіряти `TryGetValue`.
- Оператори легко комбінувати й переставляти, а кожен крок (Extract → Transform → Load) видно окремо.
- Той самий синтаксис працює для колекцій, XML, баз даних (EF Core) і паралельної обробки (`AsParallel`).
- Типобезпечність: помилки в іменах полів видно під час компіляції.

**2. Чому в аналітиці часто поєднують `Join`, `GroupBy`, `Select` та `OrderBy`?**
Дані зазвичай нормалізовані: продаж містить лише `ProductId` і `CustomerId`.
- `Join` збирає потрібні поля з різних таблиць в один рядок (ціна, місто, категорія).
- `GroupBy` переходить від окремих записів до розрізу, який цікавить аналітика (місто, місяць, категорія).
- `Select` з агрегатами (`Sum`, `Count`, `Average`) рахує показники для кожної групи.
- `OrderBy` впорядковує результат так, щоб його можна було читати: топ, хронологія.

Це аналог SQL-запиту `SELECT ... JOIN ... GROUP BY ... ORDER BY`.

**3. Які фактори найбільше впливають на продуктивність складних LINQ-запитів?**
- **Порядок операторів:** `Where` і агрегація до `Join` зменшують обсяг даних для наступних кроків.
- **Повторне перерахування:** `IEnumerable` з відкладеним виконанням, перебраний двічі, виконує весь ланцюжок двічі. Тут допомагає `ToList()`.
- **Неефективні конструкції:** `Where(...).Count()` у циклі, `First()` по великому списку замість словника, вкладені `Any`/`Contains` по `List` (O(n·m)).
- **Проміжні об'єкти** і навантаження на збирач сміття.
- **Тип ключів:** `GroupBy`/`Join` за `int` швидші, ніж за `string` чи складеним ключем.
- Сам обсяг даних, а також JIT-прогрів під час першого запуску.

**4. Як перевірити, що LINQ-пайплайн не лише працює, а й лишається читабельним і підтримуваним?**
- **Коректність:**
  - порівняти результат з незалежною реалізацією (тут `RevenueByCityManual` + `SequenceEqual`);
  - перевірити суми (дохід за містами і за місяцями дає однакову загальну суму 7 990 959 грн);
  - написати юніт-тести на невеликих наборах даних з відомою відповіддю.
- **Читабельність:**
  - кожен пайплайн оформлено окремим методом з назвою, що пояснює його мету;
  - проміжні результати мають зрозумілі імена полів (`TotalQuantity`, `Revenue`);
  - використано іменовані `record` для результатів замість кортежів;
  - один оператор на рядок, ланцюжок не довший за 8–10 кроків;
  - складні частини винесено в окремі змінні (як `customerStats` у пайплайні 4).
- **Підтримуваність:** перевірити, чи може інший розробник змінити умову (топ-5 замість топ-3, групування за кварталами), не переписуючи весь запит.
