## Реалізовані методи `CollectionUtils`

| Метод | Делегат | Що робить | Аналог у LINQ |
|-------|---------|-----------|---------------|
| `Map<TSource, TResult>` | `Func<TSource, TResult>` | Перетворює кожен елемент і повертає нову колекцію | `Select` |
| `MaxBy<T, TKey>` | `Func<T, TKey>`, `TKey : IComparable<TKey>` | Повертає елемент з найбільшим ключем | `MaxBy` (.NET 6+) |
| `Filter<T>` | `Predicate<T>` | Повертає елементи, для яких умова істинна | `Where` |
| `ForEach<T>` | `Action<T>` | Виконує дію для кожного елемента | `List<T>.ForEach` (у LINQ відповідника немає) |

Особливості реалізації:
- Усі методи перевіряють аргументи (`ArgumentNullException.ThrowIfNull`).
- `MaxBy` бере перший елемент як початковий максимум, а не `default(T)`. Тому метод коректно працює і з від'ємними числами, і з посилальними типами. Для порожньої колекції він викидає `InvalidOperationException`, як і LINQ-метод `Max`.

## Демонстрація

Методи викликаються для **чотирьох** різних колекцій: `List<int>`, `List<string>`, `List<Product>`, `Student[]`.
Використано різні види лямбд:
- вирази (`n => n * n`);
- лямбди зі складеною умовою (`n => n > 0 && n % 2 == 0`);
- лямбди, що повертають анонімний тип (`p => new { p.Name, NewPrice = ... }`);
- блочні лямбди з кількома рядками;
- замикання, що змінюють зовнішню змінну (`n => sum += n`);
- іменований метод `IsPrime`, переданий як `Predicate<int>`;
- делегати, збережені у змінних.

## Звіт

### 1. Чому делегати корисні для створення таких утиліт?

Делегат — це тип, що зберігає посилання на метод. Завдяки делегатам можна відокремити **алгоритм обходу колекції** від **дії над елементом**.
Цикл `foreach`, перевірка аргументів і збирання результату написані в `Filter` один раз, а умову фільтрації передає той, хто викликає метод.

Без делегатів довелося б писати окремі методи `FilterPositive`, `FilterEven`, `FilterExpensiveProducts` тощо, які відрізняються лише одним рядком умови. Тобто довелося б дублювати код.

Разом з узагальненнями (`<T>`) делегати роблять методи універсальними і щодо типу даних, і щодо поведінки. Один `MaxBy` знаходить і найдорожчий продукт, і найдовше слово, і студента з найвищим балом.

Стандартні делегати мають зрозумілі ролі:
- `Func<T, TResult>` — перетворення, повертає значення;
- `Predicate<T>` — умова, повертає `bool`;
- `Action<T>` — дія, нічого не повертає.

Уже з сигнатури методу видно, що саме від викликача очікується.

### 2. Як лямбда-вирази спрощують виклик цих методів?

Лямбда дозволяє описати поведінку **прямо в місці виклику**, без окремого іменованого методу:

```csharp
var expensive = CollectionUtils.Filter(products, p => p.Price > 1000);
```

Без лямбди довелося б оголосити окремий метод `static bool IsExpensive(Product p)` і передати його ім'я. Для одноразової умови це зайвий код, до того ж логіка розходиться по різних місцях файлу.

Інші переваги лямбд:
- **Виведення типів.** Компілятор сам розуміє, що `p` — це `Product`, а `TResult` у `Map(products, p => p.Name)` — це `string`. Явно вказувати узагальнені параметри не потрібно.
- **Замикання.** Лямбда бачить локальні змінні методу. Наприклад, `n => sum += n` накопичує суму в зовнішній змінній, а лічильник `index++` нумерує рядки.
- **Читабельність.** Код читається як опис: «відфільтрувати продукти, де ціна більша за 1000».

### 3. Порівняння власних методів із LINQ

| Критерій | `CollectionUtils` | LINQ (`Select`, `Where`, `MaxBy`) |
|----------|-------------------|-----------------------------------|
| Спосіб виклику | Статичний метод: `CollectionUtils.Filter(list, ...)` | Метод розширення: `list.Where(...)`. Зручно будувати ланцюжки `list.Where(...).Select(...)` |
| Виконання | **Негайне.** `Map` і `Filter` одразу обходять колекцію і створюють `List<T>` | **Відкладене** (`deferred execution`). `Where` і `Select` нічого не обчислюють, доки результат не перебирають. Через `yield return` проміжні списки не створюються |
| Пам'ять | Кожен виклик створює новий список | Елементи передаються по ланцюжку по одному, без проміжних колекцій |
| Тип умови в `Filter` | `Predicate<T>` | `Func<T, bool>` (є перевантаження з індексом елемента) |
| `MaxBy` | Ключ має реалізовувати `IComparable<TKey>` | Використовує `Comparer<TKey>.Default`, можна передати власний `IComparer` |
| `ForEach` | Працює з будь-яким `IEnumerable<T>` | У LINQ немає: LINQ призначений для запитів без побічних ефектів. Є лише `List<T>.ForEach` |
| Оптимізації | Немає | Є спеціальні шляхи для масивів і `List<T>`, оптимізації в JIT і бібліотеці |

**Висновок.** Власні методи працюють за тим самим принципом, що й LINQ: узагальнений метод плюс делегат, якому передають поведінку.
У LINQ є три переваги: відкладене виконання, методи розширення для ланцюжків і внутрішні оптимізації. Тому в реальних проєктах варто використовувати LINQ.
Власна реалізація корисна для навчання, бо показує, як LINQ влаштований усередині. Вона також знадобиться, коли потрібна поведінка, якої в LINQ немає: специфічна обробка помилок, логування кожного елемента, `ForEach` для будь-якої колекції.

## Відповіді на контрольні запитання

**1. Чому делегати зручні для передавання поведінки в узагальнені методи?**
Узагальнений метод не знає, з яким типом працюватиме, тому не може сам вирішити, як фільтрувати, перетворювати чи порівнювати елементи. Делегат дає цю логіку ззовні.
Метод відповідає лише за алгоритм (обхід, збирання результату), а конкретну поведінку визначає викликач.
Компілятор перевіряє типи: у `Filter<Product>` можна передати лише `Predicate<Product>`.

**2. Різниця між `Func<T, TResult>`, `Action<T>` та `Predicate<T>`**
- `Func<T, TResult>` приймає `T` і **повертає** `TResult`. Використовується для перетворень і обчислення ключа (`Map`, `MaxBy`). Має варіанти з 0–16 параметрами.
- `Action<T>` приймає `T` і **нічого не повертає** (`void`). Використовується для дій з побічним ефектом: вивід, запис, накопичення (`ForEach`).
- `Predicate<T>` приймає `T` і повертає **`bool`**. Це умова (`Filter`). За змістом він збігається з `Func<T, bool>`, але це окремий тип делегата, тому їх не можна напряму присвоїти один одному.

**3. Переваги поєднання generic-методів і лямбда-виразів**
Один метод працює з будь-яким типом і будь-якою логікою, тож код не дублюється.
Типобезпечність: помилки видно під час компіляції, без приведень з `object`.
Компілятор сам виводить узагальнені параметри з лямбди, тому виклики короткі.
Код виходить декларативним і читабельним: видно, *що* робиться, а не *як*.

**4. Коли корисно писати власні `Map` чи `Filter`, хоча є LINQ?**
- Для навчання: щоб зрозуміти, як працюють делегати й LINQ «під капотом».
- Коли потрібне негайне виконання з гарантованим створенням копії, а не відкладене.
- Коли потрібна додаткова поведінка: логування, підрахунок викликів, обробка винятків для кожного елемента, перевірка вхідних даних.
- Для специфічних структур даних (дерева, власні колекції), де можна обійти елементи ефективніше, ніж через загальний `IEnumerable<T>`.
- У середовищах, де LINQ небажаний через виділення пам'яті (критичні до продуктивності цикли, ігри в Unity).
